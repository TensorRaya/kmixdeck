| RQ-4 | 🟢 | 20 API names have no requirement row. They are either self-evident CRUD or read-only mirrors of PipeWire props. No requirement needed, but the *contract* must document them (RQ-3). | Covered by RQ-3. |
| RQ-5 | 🟢 | The requirements table is the best-kept artefact in the repo: numbered, RFC-2119 wording, sourced, tested, tiered, machine-audited. CT-1 is honestly 🔶 because a global shortcut needs a human keypress. | Keep. For v0.1 the README should point here as "what kmixdeck does, and how we know". |

**Verdict §7:** Requirements are real, testable and audited — better than most projects ten times this size. Two
corrections before v0.1: a hand-typed count that is already stale (RQ-1), and a D-Bus contract that documents only a
third of itself (RQ-3) although the whole architecture rests on it.

## 8 — Persistence layer

What lives where, and how it comes back.

| Data | Where | Format | Written | Read |
|---|---|---|---|---|
| Layout: channels, mixes, inputs, virtual devices, links, groups, colours, icons, FX chains, hidden devices, known apps, listening device | `$XDG_CONFIG_HOME/kmixdeck/layout.json` | JSON, `"version": 2`, v1 (`outputDevice` string) read transparently | `QSaveFile` (atomic) on every mutating call — 47 `saveLayout()` sites | daemon start; missing → `Layout::starter()` + first-run flag (UX-3) |
| Fader/mute state per node (channel, mix, cell) | PipeWire/WirePlumber `restore-stream` (the platform's own state store) — daemon re-asserts its intent when WP echoes something else (`onNode()` compare + put back) | WP's | continuously by WP | by WP at node creation; `restorePendingCellStates()` after rebuilds |
| App → channel routing | WirePlumber `restore-target` (CH-4) + `knownApps` in layout | WP's | by WP | by WP; daemon only touches apps it has never seen |
| Generated PipeWire graph | `$XDG_CONFIG_HOME/pipewire/pipewire.conf.d/kmixdeck.conf` | PipeWire conf, rendered from layout (`Layout::toPipewireConf`) | with every layout save | by PipeWire at start → **graph exists before the daemon runs** |
| Export/Import (CT-7) | user-chosen file | layout JSON + `levels[]` snapshot | on demand | Import replaces layout, applies levels |
| Web token | `$XDG_CONFIG_HOME/kmixdeck/web-token` | one line, 0600 | first `--lan` start | every start |
| Undo (CH-9) | in memory, one step | — | — | — |
| Stream Deck plugin settings | OpenAction server's own settings store (per action) | — | — | — |

Tests that pin this down: `test_dv1_layout_survives_without_the_daemon`, `test_mx3a_output_device_persists_in_generated_conf`,
`test_dv7_levels_and_mute_survive_daemon_restart`, `test_dv7_state_is_keyed_by_stable_name_not_display_name`,
`test_corrupt_layout_file_does_not_take_the_daemon_down`, `test_ct7_export_import_round_trip_…`, `test_dv6_sleep_wake_…`.

| ID | Sev | Finding | Fix |
|---|---|---|---|
| PS-1 | 🟡 | `fromJson` is tolerant (missing keys → defaults, v1 → v2) but **there is no schema document**. The only description of `layout.json` is the C++ that reads it. For a file users will hand-edit and share (Import/Export), that is not enough. | `docs/layout-format.md`: every key, type, default, since-version; one complete example. Generate the example from `Layout::starter()` in a test so it cannot drift (pairs with UT-1). |
| PS-2 | 🟡 | `"version": 2` is written, but a **newer** version is not refused — a v3 file from a future kmixdeck would be read as v2 with unknown keys silently dropped, then **saved back as v2**, destroying the user's newer data on the next change. | `fromJson`: `version > 2` → refuse to load (keep the file untouched, log, start with the starter layout, surface `FirstRun`/a notification). One `if`. |
| PS-3 | 🟢 | Fader state is delegated to WirePlumber's `restore-stream` rather than kept in `layout.json`. This is the right call (one owner of that state on the system; survives even a `kmixdeck` uninstall) and the daemon's "compare echo with intent" handles the race. | Document the decision — it surprises everyone who looks for volumes in `layout.json`. One paragraph in `docs/architecture.md`; consider ADR 0012. |
| PS-4 | 🟢 | 47 `saveLayout()` call sites, each also re-rendering the PipeWire conf. Every fader-linked change writes two files. | Fine at human rates; note it. If a frontend ever streams changes (a MIDI controller), coalesce with a 100 ms timer. |

**Verdict §8:** A clean two-layer design: *structure* in one JSON we own, *live state* in the platform's store, and the
audio graph rendered to PipeWire's config so it exists at boot without us. Atomic writes, tolerant reads, restart/hotplug/
corruption all tested. Two gaps: no written schema (PS-1) and no forward-version guard (PS-2) — the second one can eat
user data and is a one-line fix.

## 9 — Plug and play: is everything loaded automatically in operation?

The question, walked through from a cold boot:

| Step | Mechanism | Automatic? | Proven by |
|---|---|---|---|
| 1. Login → PipeWire starts | systemd user session | ✓ | platform |
| 2. Mixer graph exists (channel sinks, mix sinks, loopbacks, capture sources) | PipeWire reads `pipewire.conf.d/kmixdeck.conf` — our rendered file | ✓ **without any kmixdeck process** | `test_dv1_layout_survives_without_the_daemon` |
| 3. Apps find their channel | WirePlumber `restore-target` | ✓ | `test_ch4_…` |
| 4. Faders/mutes as left | WirePlumber `restore-stream` | ✓ | `test_dv7_…` |
| 5. Daemon starts | `kmixdeckd.service` (`BindsTo=pipewire.service`, `WantedBy=default.target`) **and** D-Bus activation (`org.kmixdeck1.service` → `SystemdService=`) — first client wakes it if the unit is not enabled | ✓ either way | `test_lifecycle` |
| 6. Daemon adopts the existing graph instead of rebuilding | `Mixer::reconcile()` — adopted nodes keep order at the end | ✓ | `test_lifecycle`, `test_dv7` |
| 7. Empty config → usable defaults | `Layout::starter()` + first-run wizard offered (UX-3) | ✓ | `test_ux3_…` |
| 8. Device unplug / replug / sleep-wake | DV-6, DV-9..12: parked, greyed, restored without restart | ✓ | `test_dv6_…`, `test_dv9_dv12_…` |
| 9. Web UI | `kmixdeck-web` is **not** started by anything — user runs it by hand | ✗ | — |
| 10. Stream Deck plugin | installed to `DATADIR/kmixdeck/streamdeck`; the OpenAction server must be pointed at it | ✗ (manual, documented in `streamdeck/README.md`) | `test_ct3_…` |
| 11. Tray icon / KDE UI autostart | no autostart entry; UI is on demand, tray appears with the UI | by design | — |
| 12. Corrupt `layout.json` | daemon starts with starter layout, keeps the bad file | ✓ | `test_corrupt_layout_…` |

| ID | Sev | Finding | Fix |
|---|---|---|---|
| PP-1 | 🟡 | The web bridge has no service unit. "Plug and play" for the phone use case means: enable once, it is there after every login. | `data/kmixdeck-web.service.in` (user unit, `After=kmixdeckd.service`, `ExecStart=… --lan`, **disabled by default** because it opens a LAN port). README: `systemctl --user enable --now kmixdeck-web`. |
| PP-2 | 🟡 | Step 2 depends on PipeWire re-reading `pipewire.conf.d` — which it does only at start. A layout change therefore takes effect live (daemon creates nodes via the API) **and** at next boot (conf). If the daemon is not running when the conf is stale (e.g. after a manual `Import` of an old file while the daemon is stopped), boot builds the old graph and the daemon reconciles on first start. This works — but nothing documents that the conf is a *cache*, not the source of truth. | `docs/architecture.md`: "layout.json is the truth; `kmixdeck.conf` is rendered from it so the graph exists before we run; the daemon reconciles on start". One paragraph. |
| PP-3 | 🟢 | Whether the systemd unit is *enabled* after `ninja install` is up to the packager (`systemctl --user enable`); D-Bus activation covers the case where it is not. | Fine. README install section must say both sentences. |
| PP-4 | 🟢 | No autostart of the UI/tray. Wave Link autostarts; a mixer whose graph exists at boot does not need to. | By design; say so in the README FAQ ("why is there no tray icon after login?"). |

**Verdict §9:** From cold boot to "apps play into the right mix at the volumes I left" — everything is automatic and
tested, and it works with zero kmixdeck processes running. The two things that are *not* automatic are the optional
frontends (web bridge, Stream Deck), and the web bridge should get a user unit (PP-1). The rest is documentation the
README owes.
